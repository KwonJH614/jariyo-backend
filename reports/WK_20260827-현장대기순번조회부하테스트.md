# 이슈 #56 현장 대기 순번 조회 부하 테스트 결과

## 개요

현장 대기 고객이 같은 매장 대기열에서 자신의 순번과 상태를 반복 조회하는 상황을 Single API와 Dual API 환경에서 측정했다. API 컨테이너별 1 CPU/2 GiB, PostgreSQL 1 CPU/2 GiB, Nginx 0.25 CPU/256 MiB 제한을 적용했다.

최종 근거는 fixed-rate polling과 시나리오별 고정 고객 할당을 적용한 다음 두 결과다.

- Single: `load-tests/issue-56/results/20260827-153453852-single`
- Dual: `load-tests/issue-56/results/20260827-153705599-dual`

두 구성 모두 Base 8 RPS와 Stressed 90 RPS를 달성했고, latency·오류율·상태 즉시 반영·SQL 정합성 기준을 모두 통과했다. 애플리케이션 공개 API, DB schema와 현장 대기 로직은 변경하지 않았다.

## 테스트 결과

### 최종 판정

| 구성 | Base peak | Base p95 / p99 | Stressed peak | Stressed p95 / p99 | 5xx·예상 밖 응답 | 전체 |
|---|---:|---:|---:|---:|---:|---|
| Single | 8 RPS | 30.288 / 82.232 ms | 90 RPS | 366.627 / 426.060 ms | 0% / 0% | `PASS` |
| Dual | 8 RPS | 29.754 / 91.968 ms | 90 RPS | 345.618 / 419.116 ms | 0% / 0% | `PASS` |

두 구성 모두 Base p95 500 ms·p99 900 ms, Stressed p95 1,200 ms·p99 2,000 ms 기준을 충족했다. 고객 polling은 각 구성에서 2,940건 수행됐고 모든 check 2,962건이 성공했다.

Dual은 Single 대비 Stressed p95를 약 5.7%, p99를 약 1.6% 줄였다. Base p95는 약 1.8% 감소했지만 p99는 약 11.8% 증가해 낮은 부하 구간에서는 로컬 측정 변동이 scale-out 효과보다 컸다.

|---|---:|---:|---:|
| 전체 현장 대기 | 180 | 180 | 180 |

| 최종 활성 대기 | 178 | 178 | 178 |

`WAITING -> CALLED -> CHECKED_IN`과 `WAITING -> CALLED -> SKIPPED -> WAITING`을 Base·Stressed에서 각각 실행했다. 상태 변경 직후 고객 상세와 마지막 순번 고객의 `waitingAhead`를 다시 조회했으며 reflection 실패는 0건이었다.

- Single 상태 반영 p95/p99: 122.198/175.307 ms
- Dual 상태 반영 p95/p99: 23.187/23.720 ms

`estimatedWaitMinutes`는 등록 시 계산해 저장하는 현재 계약대로 polling 중 동일한 값을 유지했다. 이번 검증은 동적 재계산이 아니라 저장값의 일관성을 확인했다.

### Dual 분배

Dual Nginx 로그에서 현장 대기 관련 요청 3,142건이 두 API에 정확히 1,571건씩 분배됐다. 전체 k6 HTTP 3,322건 중 나머지 180건은 고객 회원가입 요청이다.

### 읽기 경로 해석

현재 고객 상세 조회는 대기 항목·매장·서비스를 조회한 뒤 같은 매장의 당일 대기열 전체를 읽어 Java에서 `waitingAhead`를 계산한다. 180명·90 RPS에서는 기준을 충분히 통과했으므로 현재 단계에서 Redis cache를 추가할 근거는 부족하다.

향후 사용자 수나 대기열 길이가 늘어 기준을 벗어나면 cache보다 먼저 `store_id`, `operation_date`, 활성 상태, `queue_number` 조건의 DB count query로 전환하고 실제 query timing을 측정하는 편이 단순하다. cache를 도입하면 운영자 상태 변경 직후 무효화와 정합성 비용이 추가된다.

## 이슈

- Docker Desktop 4.55가 접근 불가능한 `dockerInference`와 `docker-secrets-engine/engine.sock` 고아 Unix socket 때문에 시작되지 않았다. 해당 runtime 디렉터리를 삭제하지 않고 백업 이름으로 이동해 복구했으며 이미지·볼륨·WSL 데이터는 건드리지 않았다.
- 첫 Single 측정은 정합성 SQL이 실제 컬럼 `new_status` 대신 `next_status`를 사용해 최종 판정에서 제외했다.
- 초기 polling 스케줄은 HTTP 응답시간이 sleep 주기에 누적되고 전역 VU ID가 시나리오별 고객 매핑과 충돌해 목표 RPS 상한을 넘었다. 시나리오 첫 iteration으로 고객을 고정하고 다음 예정 시각 기반 fixed-rate pacing으로 수정한 뒤 최종 측정을 다시 수행했다.
- 로컬 Docker Desktop 결과는 Fargate/RDS 절대 성능 또는 운영 수용량을 보장하지 않는다.

## 후속 작업

- 실제 AWS Fargate/RDS 구성에서 같은 fixture와 8/90 RPS 시나리오를 재측정한다.
- 대기열 길이와 RPS를 단계적으로 늘려 DB count query 전환이 필요한 변곡점을 확인한다.
- query count, PostgreSQL execution time과 connection pool 지표를 함께 수집해 API CPU와 DB 읽기 비용을 분리한다.
- Redis cache는 DB query 최적화 후에도 목표를 넘지 못하고 상태 변경 무효화 정책을 명확히 정의할 수 있을 때만 별도 이슈로 검토한다.
