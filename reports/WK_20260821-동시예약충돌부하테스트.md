# 이슈 #57 동시 예약 충돌 부하 테스트 결과

## 개요

이슈 #57에서 동일 직원·동일 슬롯의 동시 예약 정합성과 Single/Dual API 구성의 상대 성능을 재현할 전용 로컬 부하 테스트 환경을 추가했다. API container별 1 vCPU/2 GiB, PostgreSQL 1 vCPU/2 GiB 제한을 적용하고 Nginx만 호스트에 공개했다. 최종 근거는 callback 호환성 수정 후 다시 실행한 다음 두 결과만 사용한다.

- Single: `load-tests/issue-57/results/20260821-123652722-single`
- Dual: `load-tests/issue-57/results/20260821-123831748-dual`

두 구성 모두 각 슬롯에 정확히 하나의 `CONFIRMED` 예약만 생성해 정합성 기준은 통과했다. 5xx, 예상 밖 응답, setup 실패도 없었다. 그러나 두 구성 모두 최종 k6 exit code가 99였으며, 원인은 예약 결과나 무결성이 아니라 latency threshold 실패다. 따라서 전체 판정은 Single `FAIL`, Dual `FAIL`이다.

부하 테스트용 Docker/Compose/Nginx/fixture/k6/runner 자산은 추가했지만 애플리케이션의 공개 API, DB schema와 예약 logic은 변경하지 않았고 `jariyo-docs` 계약도 그대로 유지했다. corrected Single과 Dual은 동일한 애플리케이션·DB·부하 시나리오와 자원 제한으로 연속 측정했으며 두 측정 사이에 성능 tuning을 적용하지 않았다.

### 병목 해석

Single API는 106.85%, Dual의 각 API도 105.61%와 101.92%의 순간 CPU 최대값에 도달한 반면 PostgreSQL은 최대 24.70%, Nginx는 최대 3.17%였다. 다만 stats 수집 구간은 100명 signup setup과 Base/Stressed scenario 전체를 포함하고 각 frame에 timestamp가 없다. 따라서 전체 실행 중 API CPU가 1 vCPU 제한에 도달했다는 사실만 말할 수 있으며, 그 최대값이 예약 burst에서 발생했다고 귀속할 수 없다. Dual의 Stressed latency 개선은 replica 추가 효과를 보여주지만, 남은 latency 실패의 원인을 CPU만으로 단정할 수 없다.

코드상 예약 경로는 availability/conflict 작업 전에 `pg_advisory_xact_lock(hashtext(:lockKey))`를 호출하며 key는 `reservation:staff:<staffId>`다. 따라서 이번처럼 같은 staff에 집중된 요청은 API replica가 달라도 PostgreSQL transaction advisory lock을 공유해 직렬화될 가능성이 높다. 이는 코드와 scale-out 결과를 결합한 병목 추론이지 DB lock wait time을 직접 측정한 결과가 아니다. 이번 실행은 `pg_stat_activity`, `pg_locks` 또는 lock 대기 duration을 수집하지 않았으므로 PostgreSQL 대기 시간이 몇 ms였는지, 전체 latency 중 얼마를 차지했는지는 단정하지 않는다.

### 초기 callback 실패와 수정

초기 `20260821-115132160-single`, `20260821-115510020-dual` 실행은 setup 고객 100명을 만들었지만 모든 예약 시도가 로컬 k6의 `unsupported responseCallback`에서 중단돼 Nginx/API에 도달하지 않았다. peak RPS 0과 활성 예약 0은 시스템 성능이 아니라 측정 도구 호환성 오류이므로 최종 성능 근거에서 제외했다.

commit `fafd656`에서 임의 JavaScript predicate 대신 k6 1.7.1이 지원하는 `http.expectedStatuses(201, 409)` callback object를 사용했다. `409` body의 의미 검증은 기존 custom metric이 계속 담당한다. focused test, manual review, `k6 inspect`, stdin smoke를 통과한 뒤 첫 corrected `All`을 실행했다.

### 최종 측정 보완과 재실행

첫 corrected 실행 이후 final review에서 측정 계약을 다음과 같이 보완했다.

- HTTP 완료 시점의 `http_reqs` 대신 initial 요청을 보내기 직전 증가시키는 `reservation_initial_started` Counter로 dispatch RPS를 계산한다.
- runner가 Base 10~20, Stressed 50~100 dispatch RPS 범위를 직접 강제해 범위 이탈을 비정상 종료로 만든다.
- SQL integrity는 각 슬롯의 `confirmed_count=1`뿐 아니라 `matching_count=1`도 요구한다.
- PowerShell이 raw JSON timestamp를 `DateTime`으로 변환해도 원래 instant의 UTC 초를 유지하도록 정규화한다.

이 보완 뒤 세 번째 `-Mode All`을 실행해 `20260821-123652722-single`, `20260821-123831748-dual`을 만들었다. 두 결과의 dispatch 범위, 응답 의미, SQL, routing과 cleanup은 모두 통과했고 latency threshold만 실패했다. 애플리케이션 또는 DB tuning은 세 실행 사이에 없었다.

## 이슈

- Latest Single과 Dual 모두 dispatch RPS 범위는 통과했지만 latency threshold 때문에 최종 `FAIL`이다.
- Dual은 Stressed p95/p99와 Base p95를 개선했지만 Base p95/p99와 Stressed p95는 실패했다. API replica 수만 늘리는 방식은 같은 직원 lock 경합을 제거하지 않는다.
- advisory lock 대기 시간은 직접 측정하지 않았다. 현재 병목 설명은 API CPU 관측과 lock 사용 코드에 근거한 추론이다.
- Docker stats 최대값은 ANSI 제거 후 유효 frame만 파싱한 순간 최대값이며 평균 utilization이 아니다. setup과 scenario 전체를 포괄하고 timestamp가 없어 예약 burst 시점의 CPU로 귀속할 수 없다.
- Docker Desktop의 VM, host scheduling, network와 storage는 Fargate/RDS와 다르다. 이 결과는 local 상대 비교이며 AWS 절대 성능 또는 운영 capacity를 보장하지 않는다.
- 초기 callback 오류 실행은 측정 pipeline 검증에는 유효하지만 애플리케이션 성능 근거로 사용할 수 없다.

## 후속 작업

- 운영 환경과 유사한 Fargate/RDS 구성에서 동일 시나리오를 다시 측정해 local 결과와 차이를 확인한다.
- API CPU profile과 request 단계별 timing을 수집해 vCPU 사용 구간을 구분한다.
- `pg_stat_activity`, `pg_locks` 또는 별도 timing으로 advisory lock wait를 직접 측정한 뒤 lock granularity 변경 여부를 별도 이슈에서 검토한다.
- 정합성 불변식을 유지하는 검증 없이 advisory lock을 축소하거나 제거하지 않는다.
- 개선 작업 후 Base p95/p99, Stressed peak RPS/p95와 Single/Dual 상대 효과를 같은 fixture로 재검증한다.
